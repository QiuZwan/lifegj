# 生活管家 · 产品优化清单（基于 v2.11 代码实测）

整理视角：**站在用户这一侧**，按「会在哪个场景撞上」分类。
每条都标了代码依据（文件:行），不是凭空猜的；凡是我没能在设备上实测的，都会写明。

优先级口径：

| 级别 | 含义 |
| --- | --- |
| **P0** | 阻断级 —— 会导致**数据丢失**或功能不可用，必须马上修 |
| **P1** | 高 —— 关乎「管家」的核心价值、隐私基线、长期可用性 |
| **P2** | 中 —— 明显提体验，但不影响核心闭环 |
| **P3** | 低 —— 锦上添花，有余力再做 |

## 总览

| # | 模块 / 场景 | 问题 | 优先级 |
| --- | --- | --- | --- |

| 16 | 桌面 / 快捷 | 无桌面小组件、无长按快捷方式 —— 而它主打「今天要留意什么」 | **P3** |

## 一、备份与恢复（最要紧的一块）

### 1. 备份走系统剪贴板，照片一多就会失败甚至崩溃 · **P0**

- **代码依据**：`screenslife.kt:1645-1649` 的「复制备份」直接把 `store.exportState()` 塞进
  `ClipData.newPlainText`；`butlerstore.kt:924-925` 的 `BLOB_BUDGET = 8_000_000`
  说明这段文本最多会内嵌 **8MB** 的 base64（头像 / 家人照片 / 相册 / 对话图片 / 档案文件）。
- **用户会怎么撞上**：只要相册里存过十几张照片，备份文本就会超出剪贴板的实用上限
  （`setPrimaryClip` 要经 Binder 跨进程送到 system_server，实用上限约 1MB 量级）。
  更麻烦的是这段代码**没有 try/catch** —— 一旦抛异常（如 `TransactionTooLargeException`），
  点「复制备份」会**直接崩**，而不是给个提示。
  ⚠️ 诚实说明：这个上限值我是按 Binder 机制推的，**没能在设备上实测**（模拟器冻结了）。
  但「最大 8MB 的字符串 + 无异常保护」这两点在代码里是确定的。
- **建议**：
  ① 立刻给「复制备份」包 try/catch，失败时明确说「备份内容太大，请改用导出文件」；
  ② 换成**导出成文件**：用 `ACTION_CREATE_DOCUMENT` 让用户存成 `.json`（或 `.zip`），
  再走系统分享保存到网盘 / 微信文件传输助手；剪贴板那条只留作「小数据备用」。
- **预期收益**：把唯一的数据保命通道从「大概率失效」变成「可靠」。

### 2. 只能从剪贴板粘回来，没有「从文件恢复」 · **P0**

- **代码依据**：恢复入口只有 `screenslife.kt:1650-1660`（读 `cm.primaryClip`）
  + `lbdialogs.kt:430` 的多行粘贴弹窗；全项目搜 `导入` 是 **0 处**。
  而恢复校验 `butlerstore.kt:958-959` 又允许到 1200 万字符 —— 这么大一段文本，
  用户既没法从文件载入，指望它完整躺在剪贴板里也不现实。
- **用户会怎么撞上**：换了手机，按提示导出过一次备份（存在微信文件里），
  到新机器上却发现**没有地方能把这个文件读进来**。
- **建议**：加 `ACTION_OPEN_DOCUMENT` 读文件恢复；同时保留粘贴路径。
  两条入口共用同一个 `importState()`，并在恢复前做一次「这份备份有多少条记录 / 多少张图」的预览确认。
- **预期收益**：让「换机不丢数据」这句承诺真正成立。

## 二、找得到东西

### 3. 只有备忘录能搜 · **P1**

- **代码依据**：`搜索` 只出现在 `ScreensMemo.kt`（和 `butlerstore.kt` 里的备忘排序辅助），
  守护 / 订阅 / 记账 / 档案 / 任务 / 聊天**都没有搜索**。
- **用户会怎么撞上**：用了半年后，「去年那个 25 号的扣费是哪一项」只能一屏屏翻。
  订阅几十条、记账几百笔时尤其难受。
- **建议**：在首页顶部加一个「搜一搜」，跨 `tasks / subs / obligations / memos / expenses / archive / chat`
  做关键词匹配，结果**分组带类型标签**，点进去直达对应详情（复用现有的 `resolveScreen` 跳转）。
- **预期收益**：把「翻三分钟」变成「输两个字」，是数据积累后最大的体感改善。

## 三、提醒（「管家」的核心价值）

### 4. 订阅 / 义务 / 纪念日只有一条统一日报，阈值还写死 · **P1**

- **代码依据**：`reminders.kt:94-129` 的 `buildDailyDigest` 是唯一入口 ——
  订阅只报 **0–3 天**、义务和纪念日只报 **0–7 天**，数字都写死在代码里；
  只有备忘录有独立提醒（`MemoReminders`，`reminders.kt:200-246`）。
  设置项只有两个：开 / 关 + 每天几点（`butlerstore.kt:86-87`）。
- **用户会怎么撞上**：
  · 想「提前两周提醒我车险续保」—— 做不到，因为义务固定在 7 天内才报；
  · 想对某一条重要订阅单独设提醒 —— 也做不到，只能吃那条统一日报；
  · 同类事情，备忘录能设提醒、义务却不能，**能力不一致**，用户会觉得莫名其妙。
- **建议**：把 `MemoReminders` 那套（一条一个闹钟、`requestCode` 由 id 派生）**泛化**成
  「任意条目可设提醒」；在订阅 / 义务 / 纪念日的详情页给「提前 1 / 3 / 7 / 30 天」快捷胶囊；
  阈值做成用户可调。日报保留为兜底。
- **预期收益**：防止错过扣费和到期，这才是用户装它的理由。

## 四、隐私与安全感

### 5. 有相册、证件档案、健康信息，却没有应用锁 · **P1**

- **代码依据**：全项目搜 `指纹` / `生物` 是 **0 处**。而应用里存着家庭相册、
  档案库（`保单`、`续保` 这类）、血型与用药（`butlerstore.kt` 的 `bloodType` / `meds`）、
  以及全部 AI 对话记录。`help` 页也把「数据只在本机」当作卖点。
- **用户会怎么撞上**：手机借给家人 / 同事看照片，或者地铁上被人瞥到屏幕，
  私密内容一览无余。「只存本机」解决的是**上传**风险，没解决**本地可见**风险。
- **建议**：加可选的应用锁（`BiometricPrompt`，回落到 6 位 PIN）；
  开启后从后台返回时先盖一层遮罩再验身份；提供「锁相册 / 锁档案」的独立开关，
  让人可以只锁敏感模块。
- **预期收益**：把隐私承诺从「不上传」补齐到「别人拿不到」。

### 6. 删了就是真没了，没有撤销 · **P1**

- **代码依据**：`撤销` 全项目仅 1 处（且不是删除撤销）。删除路径都是
  「确认框 → 直接删」（如 `screensledger.kt:349-350` 删除花销、相册删除、
  订阅 / 任务 / 备忘删除同理）。
- **用户会怎么撞上**：误删一条「家人复诊日期」或一整组档案，
  而**没有云端可以回捞** —— 只能靠很久以前的备份。
- **建议**：删除后弹 5 秒 Snackbar 带「撤销」（先把记录留在内存里，超时才真落删）；
  或做一个统一回收站，保留 30 天，可一键清空。
- **预期收益**：本机数据类应用里，「撤销」的性价比远高于联网应用 —— 因为别无退路。

## 五、长期使用的体验

### 7. 聊天记录无上限 + 每次改动整份重写 · **P1**

- **代码依据**：`butlerstore.kt:552-554` 的 `addChat` 只做 `chat.add(...); save()`，
  **没有任何裁剪**；`save()`（`butlerstore.kt:1124`）每次都把**全部状态**序列化进
  SharedPreferences，全文件有 **58 处** `save()` 调用。
  另外 AI 提示词只用最近 8 条、诊断日志只用最近 40 条 —— 说明大量旧记录**存着但根本不用**。
- **用户会怎么撞上**：跟管家聊了几个月后，每发一条消息都要重写一整份越来越大的 JSON；
  启动时也要把整份读进内存。表现就是**越用越卡、启动越来越慢**，且用户完全不知道原因。
- **建议**：① 给 `chat` 设上限（例如保留最近 500 条，或提供「清空聊天记录」入口）；
  ② 把「易变大且非关键」的数据（chat、AI 配置）与主状态分开存，
  ③ 中期考虑迁到 SQLite / Room，让增删改不必整份重写。
- **预期收益**：避免「用了三个月变卡」这类最难解释、最伤口碑的问题。

## 六、各功能模块的可改进点

### 8. AI 管家只能新增，不能改和删 · **P2**

- **代码依据**：`aibutler.kt:330-344` 的动作表只有 `add_*` / `close_subscription` /
  `complete_task` / `toggle_dark` / `open_screen`；提示词里还**明确**写着
  「只有『删改已有记录 …』这几种才允许给空数组」（`aibutler.kt:479-480`）——
  也就是说这是**有意为之的边界**，不是漏了。
- **用户会怎么撞上**：「刚才那条记错了，改成 20」→ 管家只能回答做不到，
  用户还得自己去翻列表手动改。对话带来的顺滑感在这里断掉。
- **建议**：在**有确认**的前提下放开两类动作：`update_record`（改金额 / 日期 / 标题）
  与 `delete_record`（删单条），流程上要求管家先复述「要把 X 从 A 改成 B，对吗？」，
  用户确认后才落库。这既保住「不擅自改动」的安全感，又补上闭环。
- **预期收益**：把「能听懂」升级成「能改对」，是 AI 管家最容易被记住的一步。

### 9. 记账只有支出，没有收入，也没有预算 · **P2**

- **代码依据**：`butlerstore.kt:36` 的 `ButlerExpense(id, amount, category, note, date, at)`
  —— **没有收支类型字段**，金额恒为支出。
- **用户会怎么撞上**：想记一笔工资 / 报销没地方放；想设「这个月餐饮别超 1500」
  也没地方设，月报只能说「花了多少」，说不出「超没超」。
- **建议**：加 `type`（支出 / 收入）与可选的**月度预算**（总额 + 分品类），
  超支时在首页和日报里提示。收入可以只在月报里做「收入 / 支出 / 结余」三行。
- **预期收益**：从「流水记录」升级成「能管的账」。

### 10. 已知金额与日期的订阅，不会自动变成预期支出 · **P2**

- **代码依据**：`ButlerCharge`（`butlerstore.kt:39`）的注释明确写着
  「只由用户手动记录，或扫描 / 通知真的命中时写入；**不由程序推算**」——
  这是出于诚信约定的设计取舍，不是 bug。
- **用户会怎么撞上**：「这个月还有多少钱要扣」得自己心算；记账与订阅是两个互不相干的模块。
- **建议**：**保留**「不伪造已扣」的底线，但可以把订阅按 `nextDate` 明确标成
  **「预期支出（尚未发生）」** 单独一栏，与被证实真实发生过的 `ButlerCharge` 分开展示。
  这既不算推算造假，又能回答用户真正想问的问题。
- **预期收益**：让「订阅」和「记账」第一次产生联动，同时不破坏现有诚信口径。

### 11. 订阅不会发现涨价，试用期到期也不提醒 · **P2**

- **代码依据**：`ButlerClosedSub` 只记「关闭」，没有历史价格序列；
  `ButlerCharge` 有 `amount` 但没有任何「与上次对比」的逻辑。
- **用户会怎么撞上**：包月悄悄从 15 涨到 20，用户永远不会知道 ——
  而这恰恰是「管家」该替他盯着的事。
- **建议**：当同一订阅的新一笔 `ButlerCharge` 金额**大于**上一次时，
  在守护页标一条「比上月贵了 ¥5」，并在日报里提一次。
  同时给订阅加可选「试用截止日」，到期前 1 天提醒。
- **预期收益**：这是最容易让用户觉得「它真在帮我省钱」的一类主动提醒。

### 12. 档案单文件 4MB 上限，超了不给替代路径 · **P2**

- **代码依据**：`butlerstore.kt:393` 注释「单文件上限 4MB」；
  `screenslife.kt:2573` 的提示是「没能存入：单份可能超过 4 MB，或文件读不到」。
- **用户会怎么撞上**：想存一份扫描版合同（常见就是 5–10MB）被拒，
  而提示只说「没能存入」，用户不知道该怎么办。
- **建议**：图片类**入库前自动压缩**（复用已有的 `saveShrunk`，全项目唯一降采样入口）；
  非图片超限时明确说「这个文件 8.2MB，超过 4MB 上限 —— 可以压缩后再试」，
  并给一个「仍然要存」的最大值说明。空口拒绝不如给条路。
- **预期收益**：减少一次「它坏了」的误判，同时保住体积可控。

### 13. 相册与档案互不相通 · **P2**

- **代码依据**：`album` 与 `archive` 是两套独立列表（`butlerstore.kt` 的
  `album` / `archive`，各自有 `addAlbumPhotos` / 档案导入，互不引用）。
- **用户会怎么撞上**：拍了一张保单照片进了相册，想把它归到「保单」这组档案里 ——
  得**重新拍/重新选一次**；反过来，档案里的图片也无法在相册里浏览。
- **建议**：在相册的查看器里加「归入档案 →」；在档案详情里允许「从相册选」。
  两边都只是引用已有的本机文件（注意别复制出两份，避免盘上重复）。
- **预期收益**：把两个孤岛连起来，符合用户对「一个管家」的直觉。

## 七、可访问性与上手

### 14. 小字多、写死高度多，放大字体后有截断风险 · **P2**

- **代码依据**：随手可见 10.5sp / 11sp / 12sp（如 `screensabout.kt` 多处、
  `screenstoday.kt` 的辅助行），同时不少容器用了固定 `.dp` 高度或 `size(...)`。
  好的方面：`contentDescription` 有 74 处，无障碍标注意识是有的。
- **用户会怎么撞上**：长辈把系统字体调到「大」，一行说明文字变成两三行，
  固定高度的行会把字**裁掉**（尤其是状态胶囊、列表副标题）。
- **建议**：① 说明性文字最低从 11sp 起；② 固定高度改 `heightIn(min = ...)`；
  ③ 拿 1.3× 和 2.0× 两档字号各过一遍所有页面截图，逐页看有没有截断。
- **预期收益**：直接决定它能不能被长辈用起来 —— 而这个产品的目标人群里就有他们。

### 15. 没有「三步上手」 · **P3**

- **代码依据**：全项目只有天气那一个一次性引导弹窗（`screenstoday.kt:113-159`）；
  空态文案有 21 处（做得不错），但没有首次使用的流程。
- **用户会怎么撞上**：第一次打开面对五个空页面，不知道从哪开始 ——
  尤其「守护 / 义务」这种自造名词，光看名字猜不出是干嘛的。
- **建议**：首启一次性 3 步引导（加一个订阅 / 记一笔 / 跟管家说一句话），
  每步都能跳过，且**不塞任何演示数据**（守住现有的干净首装约定）。
- **预期收益**：把「装完不知道干啥」转成「三分钟就有一个真实记录」。

### 16. 没有桌面小组件 / 快捷方式 · **P3**

- **代码依据**：无 `AppWidget`、无 `Shortcut`。
- **用户会怎么撞上**：它主打「今天有什么要留意」，但用户必须**先打开 App** 才知道 ——
  而这条信息本来就该在桌面上就能看到。
- **建议**：做一个 4×2 小组件，显示「最近一笔扣费 / 最近一件到期 + 待办条数」，
  点击直达守护页；再加两个长按快捷方式（记一笔 / 跟管家说一句）。
- **预期收益**：提升打开频次 —— 日活类工具的常规放大器。

## 建议的动手顺序

1. **先修 P0（第 1、2 条）** —— 备份是唯一的数据保命通道，现在处在「用户以为有、实际大概率用不了」的状态，风险等级最高。
2. **再做 P1 里性价比最高的两条**：应用锁（第 5）与撤销（第 6）—— 改动面小、用户感知强。
3. **然后是提醒泛化（第 4）** —— 工程量中等，但它决定「管家」这个名字是否名副其实。
