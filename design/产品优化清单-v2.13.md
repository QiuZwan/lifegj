# 生活管家 · 产品优化清单（基于 v2.13 代码现状）

上一份清单是 `design/产品优化清单-v2.11.md`，那 16 条已在 **v2.12 全部落地**（备份走文件、应用锁、
删除可撤销、全局检索、提醒泛化、收入与预算、订阅预计支出、AI 可改可删、档案自动压缩、
相册⇄档案引用、首启引导、小组件与快捷方式、小字 11sp 起）。**本清单不重复那些已修的**，
只看 v2.13（versionCode 27）**当前代码里还站得住的问题**。

整理视角仍然是**站在用户这一侧**：按「会在哪个场景撞上」分类，每条都给代码依据（文件:行）。

> ### 关于证据强度（先说清楚）
> 本轮**没有做设备实测** —— 手边的模拟器此前多次冻结（见 `2026-09-22` 日志），
> 因此下面每条的依据都是**读代码 + 读 readme 得出**，不是截图证实的。
> 凡属"我按机制推断、但没实测"的，都在条目里单独标了出来。
> 需要实机确认的，建议按文末「验证方式」逐条跑一遍再动手。

优先级口径（沿用上一份）：

| 级别 | 含义 |
| --- | --- |
| **P0** | 阻断级 —— 数据丢失或功能不可用，必须马上修 |
| **P1** | 高 —— 关乎「管家」的核心价值、隐私承诺、数据可信度 |
| **P2** | 中 —— 明显提体验，但不影响核心闭环 |
| **P3** | 低 —— 锦上添花，有余力再做 |

## 一、备份与恢复（唯一的数据保命通道）

### 1. 导出备份会「静默漏文件」 · **P1**

- **代码依据**：`butlerstore.kt:1473-1487` 的 `exportState()` 用一个**全局共享**的预算往下发：
  `var budget = BLOB_BUDGET`（8 MB），每个文件 `if (enc.length > budget) return`
  —— **额度用光就直接跳过，不抛错、不记录、不在备份里留任何痕迹**。
  遍历顺序是 `avatar → members → album → chat → archive`。
- **用户会怎么撞上**：相册存了几十张照片（每张 base64 后约 200–400 KB），8MB 在相册那一步就见底了；
  后面**对话图与档案文件全部没进备份**。而导出时界面只弹一句「备份已存成文件」——
  用户会一路以为"全备好了"，**直到换机恢复时才发现档案文件是空的**。
  这与项目自己的「诚信约定」直接冲突：这属于"看起来成功了，其实没有"。
  ⚠️ 诚实标注：8MB 这个预算在代码里是确定的；**"相册几十张就会用光"是按单张体积估算的**
  （照片压缩到长边 1024，实测量级需要装一次机确认）。
- **建议**：
  ① `putFile` 跳过时把文件名记进一个 `skipped` 列表，导出后**如实告诉用户**：
  「这次有 12 个文件因体积上限没能进备份（相册 9 / 档案 3）」；
  ② 更好的做法是**按类别分预算**（相册 / 档案各自一份），而不是先到先得；
  ③ 长期看，大文件不该 base64 进 JSON —— 备份打成 zip 更合理。
- **预期收益**：把「以为备份了」变成「知道备份了什么」，这是保命通道的底线。

### 2. 恢复前没有「这份备份里有什么」的预览 · **P1**

- **代码依据**：`screenslife.kt:1955-1959` 的二次确认弹窗，正文是**写死的**一句
  「将覆盖当前全部数据（待办 / 订阅 / 对话 / 家人 / 相册 / 照片），无法撤销」——
  它**没有解析这份备份**，所以显示不出条数与张数。
  而 `readme.md:142` 明确写着：「恢复前先给预览（这份备份里有多少条记录、多少张图），确认后才落库。」
- **用户会怎么撞上**：手机里存着好几份备份（不同日期的），选的时候没有任何依据 ——
  不知道哪份更新、哪份里有没有那组保单。选错就是覆盖，且**无法撤销**。
- **建议**：在 `restorePending = raw` 之后先解析一次（复用 `isValidBackup` 里已有的 `JSONObject(raw)`），
  在确认弹窗里列出「订阅 12 · 待办 30 · 相册 24 张 · 档案 5 组 · 备份内文 xx KB」，
  有 `fileBlobs` 时把件数也列出来。**做不做得到是小事，readme 写了的就必须做到**；
  如果暂不做，就得把 readme 那句删掉 —— 不能让文档替代码撒谎。
- **预期收益**：让"覆盖恢复"这个不可逆操作变成有依据的决定。

### 3. `isValidBackup` 判断过宽 + 整体覆盖 · **P2**

- **代码依据**：`butlerstore.kt:1495-1503`：
  `o.has("tasks") || o.has("subs") || o.has("name")` —— 第三个条件是致命的宽松，
  **任何一个带 `name` 字段的 JSON 都会被判成"像生活管家的备份"**。
  而 `importState()`（`butlerstore.kt:1521-1525`）会把 `state_v1` **整份替换**掉。
- **用户会怎么撞上**：换机时从"最近文件"里随手选错一个 `.json`（比如某个 App 的导出配置），
  只要它带 `name`，就会通过校验、进到确认弹窗、点「覆盖恢复」→ **本机记录被清成一份无关数据**。
  `hasAnyRecord()` 随后为假，界面回到全新空态，用户以为数据丢了。
- **建议**：加一个明确的**格式指纹**字段（例如导出时写入 `"app":"lifebutler"` + `"v":1`），
  校验时**必须命中**才认；`name` 这个条件直接删掉。
  另外恢复前可先提示"当前本机已有 N 条记录，恢复会全部替换"。
- **预期收益**：堵掉一条"点两下就清空全部数据"的路。

### 4. 恢复不清旧文件 + 文件通道没有体积上限 · **P2**

- **代码依据**：
  · `butlerstore.kt:1506-1529` 的 `importState()` 只做「写入新文件 + 换掉 JSON + 重载」，
    **没有任何一步去删旧文件**（`clearAll()` 里才有删盘逻辑，而恢复路径没走它）。
  · `backupio.kt:54-60` 的 `read()` 是 `bufferedReader().readText()` ——
    **整个文件一次性读进内存**，没有任何长度保护；
    粘贴那条路径有 `raw.length > 2_000_000` 的拦截（`screenslife.kt:1941`），
    而**文件路径没有对应拦截**，只有读完之后 `isValidBackup` 里的 12MB 事后检查。
- **用户会怎么撞上**：
  · 换机恢复后，手机上**同时存在**旧数据留下的照片与恢复进来的照片，占双倍空间；
    如果旧数据是"不想被别人看到"的内容，**它其实还在盘上**。
  · 从一个共享目录/聊天记录里误选到一个几百 MB 的 json → 直接 OOM 闪退（用户看不懂为什么）。
- **建议**：① 恢复成功后清理不再被 `members / album / chat / archive` 引用的本机文件
  （参照 `clearAll()` 的前缀规则）；② 文件通道读之前先看 `contentResolver` 给的
  `OpenableColumns.SIZE`，超过 12MB 就先拒绝并说明。
- **预期收益**：恢复后磁盘状态干净；不再有"读一个文件把 App 读崩"。

## 二、隐私与安全感

### 3（总表 #3）. 应用锁不盖通知内容 · **P1**

- **代码依据**：`reminders.kt:203-219` 的 `post()` 构建通知时只设了
  `setSmallIcon / setContentTitle / setContentText / BigTextStyle / setContentIntent / setAutoCancel`
  —— **没有 `setVisibility(VISIBILITY_SECRET)`，也没有把锁屏可见性关掉**；
  `postMemoReminder()`（`reminders.kt:180-201`）同样如此，而且它是 `IMPORTANCE_HIGH`，
  还会把备忘正文第一行（最多 90 字）直接放上去。
- **用户会怎么撞上**：他之所以去「我的 → 应用锁」把锁打开，就是因为不想让别人看到相册、
  证件档案与血型/用药。结果**锁屏上依然明文躺着**「「XX会员」明天扣费 ¥25」
  「明天下午三点去物业交费」—— 借手机给同事看一眼、或手机放桌上，全被人看见。
  **锁只锁了 App 内部，没锁住提醒。**
- **建议**：应用锁开启时，给两个渠道都设 `setVisibility(VISIBILITY_SECRET)`（锁屏上不显示内容），
  或按用户选择给一个"通知不显示内容"的开关（Android 系统里那个 `setPublicVersion` 也够用：
  公开版只写「生活管家有 1 条提醒」）。**至少要在应用锁页面上说清"通知不在保护范围内"**。
- **预期收益**：把隐私承诺从"App 里有锁"补齐到"锁屏上也看不见"。

### 9. 桌面小组件明文展示，没有隐藏开关 · **P2**

- **代码依据**：`lbwidget.kt:53-58`，标题与正文直接取 `Notifier.buildDailyDigest()`
  的两段文本（「今天有 3 件要留意」「「XX」明天扣费 ¥25；…」），点击目标只分"整块 → 对应页"与
  "正文 → 记账本"。**没有任何"模糊显示"或"只显示条数"的选择。**
- **用户会怎么撞上**：他刚在 App 里开了应用锁，回到桌面却发现：**扣费明细就明写在桌面上**，
  而且任何人拿起手机（还没解锁）都能看到。两个功能互相拆台。
- **建议**：给小组件一个显示档位（**完整 / 只显示条数 / 隐藏正文**），默认跟应用锁联动
  （应用锁开着就默认只显示条数）。另外「正文区域点击 → 记账本」这个映射很反直觉
  （点正文通常想要"看详情"），建议正文也进对应详情页，"记一笔"单独给一个小按钮。
- **预期收益**：让"桌面能看"与"不想被别人看"两个诉求不打架。

### 10. 设了锁屏，App 里仍说"锁不生效" · **P2**

- **代码依据**：`butlerlock.kt:72`：`val secure = remember(ctx) { km?.isDeviceSecure == true }`
  —— **只在 ctx 变化时才算一次**，之后永远用缓存值。而同文件的 `foregroundTick`
  明明就是"回到前台"的信号，却没有被用作 key。
- **用户会怎么撞上**：按 App 给的提示去系统里设好锁屏，回到生活管家 —— 界面**仍然是**
  「应用锁现在不生效，本机还没有设置锁屏密码…」+「暂时进入（不锁）」。
  用户会以为"我设了它没认"，反过来怀疑锁屏没设成功，甚至怀疑应用锁是坏的。
- **建议**：把 `remember(ctx)` 改成 `remember(ctx, foregroundTick)`（回来必然重算一次），
  或者在遮罩页加一个"我设好了，重新检查"的按钮。
- **预期收益**：消掉一个"按你说的做了却没变化"的挫败感，这类反馈最容易引发不信任。

## 三、每天的第一屏（今日）

### 4（总表 #4）. 首页只有 2 条，与简报说不上话 · **P1**

- **代码依据**：`screenstoday.kt:176-184` 的「替你盯着的」**只取两个东西** ——
  `nextSub`（最近一笔要扣费的订阅）与 `nextOb`（最近一件到期义务），
  计数 `watchCount` 也只有这两项的和（上限 2）。
  而 `reminders.kt:100-156` 的 `buildDailyDigest()` 汇的总数**远不止**：
  订阅（含试用到期与涨价）、义务、关键日期、**家人的日期**、以及待办，
  标题写的是「今天有 N 件要留意」，`take(3)` 之外还会补一句「等 N 项」。
- **用户会怎么撞上**：桌面上、锁屏通知上写着「今天有 5 件要留意」，点开 App 首页，
  「替你盯着的」却只有 2 条 —— 而且**剩下那 3 条里可能就有他真正想看的那条**
  （妈妈的复诊、结婚纪念日、试用到期）。用户只能自己去别的页面翻，
  "打开 App 就知道今天该干嘛"这个主打承诺在这里断掉了。
- **建议**：首页的「替你盯着的」直接**复用 `Notifier.buildDailyDigest()` 的那份数据源**
  （或把它的汇总逻辑抽成一个公共函数返回条目列表），按紧急度排前 3–5 条，
  同类折叠成"还有 3 件"。**关键是两处口径必须同源** —— 否则桌面上说 5 件、
  首页说 2 件，用户会同时不信两个（这正是小组件与通知共用 `buildDailyDigest` 的初衷，
  首页却漏在外面）。
- **预期收益**：首页真正成为"今天要留意什么"的答案页，而不是两个入口卡。

### 11. 首页不提预算超支 · **P2**

- **代码依据**：`budgetStatus()` 全项目**只被调用一次**（`screensledger.kt:144`）。
  首页 `screenstoday.kt` 只显示「今天花的钱」与月报入口，没有预算相关。
  而 readme 的 v2.12 一节写着预算可以「看进度与超支」，清单原文写的是
  「超支时在首页和日报里提示」。
- **用户会怎么撞上**：他设了「这个月别超 3000」，然后**只有主动打开记账本才知道超没超**。
  首页每天报"今天花了多少钱"，却对"本月已经超了"这件事一言不发 ——
  而那正是他设预算的原因。
- **建议**：`budgetStatus()` 非空且 `over == true` 时，在首页「今天花的钱」卡片里加一行
  「本月已超 ¥320（预算 ¥3000）」，并在 `buildDailyDigest` 里加一条同类提醒。
  没设预算仍然什么都不说（守住"不替用户假定预算"的底线）。
- **预期收益**：让预算这个功能真的起作用，而不是一个只有主动打开才看得见的数字。

### 12. 家人的事在首页不露面 · **P2**

- **代码依据**：`screenstoday.kt` 里没有任何 `members` / `keyDates` 的引用；
  这两类只有在 `buildDailyDigest()`（`reminders.kt:128-141`）和「家庭」页出现。
- **用户会怎么撞上**：这个 App 的「家庭」是这个产品的差异点，但首页那一屏
  （用户一天里唯一必然会看到的一屏）对家人的复诊、生日、纪念日**只字不提** ——
  他得先想到"去看看家庭页"。
- **建议**：把"最近一件家人的日期"并入首页「替你盯着的」（与第 4 条一起做，同一处改动）。
- **预期收益**：让"家庭"从第二个 tab 变成首页上就会主动提醒的东西。

## 四、扣费自动捕获（扫描 / 通知）

### 6（总表 #6）. 通知一命中就自动落真账 · **P1**

- **代码依据**：`subscanner.kt:244-256`，`recordNotification()` 在解析成功后**无条件**做三件事：
  `store.addCharge(...)`（写进真实扣费流水）、`store.addScannedSub(...)`（自动加进守护清单）、
  `store.addChat(false, "已自动放进守护清单…")`。用户**全程没有参与**。
  而它的判据 `STRONG_N`（`subscanner.kt:105`）是
  `(自动续费|自动扣款|免密支付|代扣|已扣款|扣款|支出|付款|续费)` —— 含「支出」「付款」，
  覆盖面相当宽；排除词只有 `(退款|退货|入账|转入|转账|工资|红包|验证码|登录)`。
- **用户会怎么撞上**：微信里"向某某付款 500 元"这类通知（不带"转账"二字）会命中「付款」，
  于是 —— **守护清单里凭空多出一个"订阅"、记账流水里多出一笔 500 元扣费**。
  他事后看到只会觉得"这个东西在乱记我的账"，而账目一旦被污染，整个记账模块的可信度就没了。
  ⚠️ 诚实标注：**具体哪类通知会被误命中我没有实测**（没装热门 App 的通知环境），
  但"关键词表含「支出/付款」+ 命中即落真账"这两点在代码里是确定的，
  误命中的**代价**（写进真实流水、只能靠手动删）也是确定的。
- **建议**：把自动落库改成**"线索待确认"**：命中的通知先写进一个"待认领"清单
  （守护页顶部一张卡：「收到 2 条扣费线索，是订阅吗？认得 / 不是」），用户点一下才
  `addCharge` / `addScannedSub`。这与产品既有的两条口径一致 ——
  「AI 改删要先确认」「不伪造已扣」。关键词表也应把「支出」「付款」降级为弱信号
  （需同时出现商户名与金额才认）。
- **预期收益**：保住记账与守护清单的可信度 —— 这是自动捕获功能存在的全部意义。

### 13. 「通知使用权已开启」会假阳性 · **P2**

- **代码依据**：`subscanner.kt:197-204` 的 `notificationsEnabled()` 只读了一件事：
  `Settings.Secure.getString(cr, "enabled_notification_listeners")` 里**有没有本包名**。
  它**不检查 `NotifListenerService` 这个实例是否真的被系统连上了**。
- **用户会怎么撞上**：系统有时会把通知监听服务断开（省电策略、异常重启），
  而设置里那条授权**仍然在**。于是 App 内显示"已开启"，用户以为在收扣费通知，
  实际一条都没进来 —— 他会以为是"扫描不准"，而不是"根本没在工作"。
  这类"看起来在跑其实没跑"的静默失败，是本项目最忌讳的一类问题。
- **建议**：在 `NotifListenerService` 里用一个静态标记记录"连上了/断开了"
  （`onListenerConnected` / `onListenerDisconnected`），
  界面判断改成**两个条件都满足**才说"已开启"；断开了就如实说"系统断开了这个权限，
  点这里去重新开启"。
- **预期收益**：把"功能到底有没有在工作"这件事说清楚。

### 14. 只认 15 个包名，且没说清在听什么 · **P2**

- **代码依据**：`notiflistenerservice.kt:35-53` 的 `WATCHED` 是一个**写死的 15 个包名**的集合
  （微信、支付宝、云闪付 + 12 家银行）。界面（1.9 起）只说"开启通知使用权"，
  没有地方**列出这几个应用**，也没有说明"其余通知不解析、不保存"。
- **用户会怎么撞上**：
  · 他的卡是没列进去的那家银行（或地方农商行、微信支付分、美团月付）→
    **开了权限却永远扫不到任何东西**，他会判定"这个功能是坏的"。
  · 反过来，在意隐私的用户看到系统那句「生活管家可以读取你的**所有**通知」会直接不敢开
    —— 系统设置页的措辞是改不了的，**只能靠 App 自己讲清楚**。
- **建议**：① 在扫描页/权限说明里**列出正在监听的 App 名单**（直接由 `WATCHED` 渲染，
  加包名只改一处）；② 写明"其余应用的通知不解析、不保存，代码里只筛上述包名"；
  ③ 允许用户**手动补一个包名**（给个输入框），把"扫不到"变成"可以自己加"。
- **预期收益**：把"重权限"的信任成本降下来，同时减少"它没用"的误判。

## 五、记账

### 5（总表 #5）. 不能补记昨天、也改不了日期 · **P1**

- **代码依据**：
  · `butlerstore.kt:1119-1129` 的 `addExpense(...)` 签名里**没有日期参数**，
    日期写死 `LocalDate.now().toString()`；
  · `butlerstore.kt:1131-1142` 的 `updateExpense(...)` 也**不含 date**，`copy` 里没动它；
  · `screensledger.kt:532-688` 的 `ExpenseAddDialog` 只有 金额 / 分类 / 备注 / 收支开关四项。
- **用户会怎么撞上**：这是最日常的场景 —— **昨晚忘了记，今天早上补**。
  他记完这一笔，它就落在"今天"，于是"今天花了 85"里混进了昨天的 60，
  而昨天显示的又是 0。整个"近 7 天"趋势条跟着一起错位。
  他唯一的办法是**骗自己**（记成今天），或者放弃补记。
  另外自动捕获进来的那笔扣费金额不准时，**也没有办法改日期**。
- **建议**：在 `ExpenseAddDialog` 里加一个日期行，默认"今天"，
  点开复用项目里已有的**日期选择器**（订阅/义务那边早就有"今天/昨天/一周后"快捷与月份导航，
  这里直接用同一套，别另写一个）；`addExpense` / `updateExpense` 加 `date` 参数，
  默认值保持 `LocalDate.now()` 以免影响既有调用点。
- **预期收益**：补齐记账最基础的一条能力 —— 能补记，账才是准的。

### 17. 分类固定 8 个，不可自定义 · **P2**

- **代码依据**：`screensledger.kt:78` 的 `LB_EXPENSE_CATEGORIES` 是写死的 8 项
  （餐饮/交通/购物/居家/娱乐/医疗/人情/其他）；而备忘录的分类是**可增删的**
  （`memoCategories` + `addMemoCategory` / `removeMemoCategory`，`butlerstore.kt:1079-1106`）。
- **用户会怎么撞上**：有孩子的人想加「教育」、养宠物的想加「宠物」、还贷的想加「房贷」——
  都只能塞进「其他」。「其他」越滚越大之后，分类统计就失效了。
  他还会发现：**备忘录能自己建分类，记账却不能** —— 同一个 App 里两套规矩，很莫名其妙。
- **建议**：把分类列表做成与备忘录同构的"可增删自定义 + 一套默认值"，
  存进 `state_v1`（**新增集合要按约定改六处**：`save`/`load`/`clearLists`/`clearAll`/
  `hasAnyRecord`/`exportState`+`applyRestoredFiles`）。删除分类时把账目改挂"其他"，
  **不删任何记录**（照抄备忘录那套处理）。
- **预期收益**：让分类统计在用了半年之后仍然有意义。

### 18. 「全部记录」一次性全渲染 + 每帧重算 · **P2**

- **代码依据**：`screensledger.kt:139` 把全部账目 `groupBy { it.date }`，
  然后在 `397-451` 用 `groups.forEach { ... }` + `LbCard` **把所有分组所有条目一次组合出来**
  （`Column`，不是 `LazyColumn`）。
  另外 `133-138` 的"近 7 天"是 `(0..6).map { store.expenses.filter { ... } }` ——
  **每次重组都要对全表扫 7 遍**；`141-144` 的月度合计同理；而整个 `ExpenseScreen`
  **没有一处 `remember`**，任何 state 变化（包括弹窗开关）都会把上述全部重算一遍。
- **用户会怎么撞上**：记到几百笔之后，打开记账本要等；每滚一下就掉帧；
  点一下「记一笔」弹窗，背后的整页统计又重算一次。
  ⚠️ 诚实标注：**具体卡到什么程度我没有实测**（模拟器冻结），
  但"非懒加载 + 无记忆化 + 每次重组 7 次全表扫描"是代码事实，数据量上去必然体现。
- **建议**：① 「全部记录」改 `LazyColumn`（或至少分页，先渲染最近 N 天，"加载更早"再取）；
  ② 统计量用 `remember(store.expenses.toList())` / `derivedStateOf` 包起来，
  ③ "近 7 天"一次遍历算完，别扫 7 遍。
- **预期收益**：让"用了半年之后仍然顺手"。

## 六、提醒（「管家」的核心价值）

### 15. 家人的日期不能单独设提前量 · **P2**

- **代码依据**：`reminders.kt:136-141`，`store.members.forEach` 用的提前量是**全局的**
  `dueAhead`（`store.reminderDueDays`）；而订阅、义务、关键日期都先过了一层
  `store.aheadDaysFor(x.remindAhead, 全局值)`（`reminders.kt:112 / 122 / 129`）。
  也就是说 `ButlerSub / ButlerObligation / ButlerKeyDate` 有 `remindAhead` 字段，
  **家人的记录没有**。
- **用户会怎么撞上**：v2.12 的说明里写得很清楚 ——「订阅 / 义务 / 关键日期都能单条设
  提前 1/3/7/30 天…不再出现『备忘能设、义务不能设』的不一致」。
  现在**同样是这个不一致，只是换成了家人**：妈妈的复诊想提前两周知道，
  和"纪念日提前 7 天"只能共用一个数。
- **建议**：给 `ButlerMember` 加 `remindAhead`（标量，只需改 `save` 的 `put` + `load` 的 `opt`），
  在家人编辑弹窗里放同一排「提前 1/3/7/30 天」胶囊 —— 复用订阅详情页那套 UI，别另做。
- **预期收益**：把 v2.12 那句"能力一致"真正补完。

### 16. 试用到期只在 0–1 天报 · **P2**

- **代码依据**：`reminders.kt:109`：`if (trial != null && trial in 0L..1L)` ——
  **硬编码 0 与 1**。而同一段代码里，订阅扣费、义务、纪念日都已经走
  `aheadDaysFor(...)` 的用户可配置提前量了。
- **用户会怎么撞上**：试用到期是**最需要提前量**的一件事 —— 提前 1 天收到"明天开始收费"，
  而那时候他正忙着，很容易就忘了，第二天钱就扣掉了。想提前 3 天知道？做不到。
- **建议**：试用也走 `aheadDaysFor(sub.remindAhead, subAhead)`（或单独给一个默认 3 天的值），
  不要再写死。措辞保持现在的口径（「免费到此为止」而不是「开始收钱」）。
- **预期收益**：这正是用户装这个 App 的核心动机 —— 别让他错过该拦的那一笔。

### 24. 简报每天覆盖，渠道优先级不可调 · **P3**

- **代码依据**：`reminders.kt:218` 用**固定 id `1001`** 发每日简报 —— 今天那条会**覆盖**昨天没看的那条；
  备忘提醒用的是 `2000 + hash`（`198`），所以备忘会累积、简报不会。
  另外两个渠道的重要度是写死的：每日简报 `IMPORTANCE_DEFAULT`（`85`），
  备忘提醒 `IMPORTANCE_HIGH`（`171`）。
- **用户会怎么撞上**：如果连续几天没点开通知，他只能看到最新一条；
  而且"扣费提醒"这件事的重要度**低于"备忘提醒"**，默认没有提示音（或不横幅）。
- **建议**：每日简报也用日期派生的 id（让未读的能并存几条，
  但保持"同一天只有一条"），并把每日简报的渠道重要度提到与备忘一致 ——
  或者把重要度选择权交给渠道设置（Android 本来就让用户在系统里调，前提是渠道描述写清楚）。
- **预期收益**：漏看一天不会把该做的事一起丢掉。

## 七、搜索与撤销

### 19. 边打字边全库扫描 · **P2**

- **代码依据**：`screenssearch.kt:74`：`val hits = store.searchAll(q)` **直接写在 composable 体内**，
  没有任何 `remember` / `derivedStateOf` / 防抖。
  `searchAll()`（`butlerstore.kt:1030-1060`）在每次调用里对 **11 类数据**做 `filter + contains`，
  其中包含**最多 500 条对话**（每条还要 `lineSequence().first()`）与全部记账明细。
- **用户会怎么撞上**：每敲一个字，整页重组 → 全库重扫 → 再分组渲染。
  数据攒起来之后，**输入框会开始有明显的延迟感**（打字掉字、光标跟不上）。
- **建议**：`remember(q, store.tasks.toList(), …)` 或 `derivedStateOf { store.searchAll(q) }`，
  再加一个 150–250ms 的防抖（`snapshotFlow { q }.debounce(...)`）。
  这不是"优雅"，是这个页面唯一的输入路径。
- **预期收益**：保证最常用的入口在数据多了以后仍然跟手。

### 20. 搜到了，但跳不到那一条 · **P2**

- **代码依据**：`butlerstore.kt:1036-1057` 构造 `SearchHit` 时，**只有"订阅"把
  `subId` 填成了自己的 id**（`SearchHit("订阅", it.id, it.name, ..., "guard", it.id)`），
  其余全是 `null`。
  于是 `mainactivity.kt:312-320` 的分支里，只有订阅能进 `overlay = "detail"`，
  其他一律 `openRoute(route)` —— 而 `openRoute`（`271-280`）对
  `"today" / "guard" / "family"` 只是切 tab，**不定位任何一条**。
- **用户会怎么撞上**：搜"房贷"，结果显示"待办 · 房贷还款"，
  点进去 → 落在**今日页顶部**，那一屏可能有十几条待办，他还是要自己找。
  搜到一条三个月前的扣费流水，点进去落在守护页顶部 —— 等于**没跳**。
  用户会觉得"搜是搜到了，但没用"。
- **建议**：给 `SearchHit` 补上"定位信息"（待办/义务/记账/备忘都已有 id），
  各页支持一个 `highlightId` 参数：进来后滚到那一条并短暂高亮。
  工作量不大（各列表本来就渲染 id），但直接决定搜索功能的口碑。
- **预期收益**：把"搜得到"变成"一步就到"。

### 21. 撤销只有一步 · **P2**

- **代码依据**：`butlerstore.kt:672-679` 的 `rememberUndo()` 第一件事就是 `closeUndoWindow()` ——
  **它会把上一次的 `onDiscard` 立刻执行掉**（也就是把上一次删的本机文件真删了），
  然后把新的 `restore` 覆盖上去。
- **用户会怎么撞上**：他连着删了两张误传的相册照片（很常见），然后想撤销**第一张** ——
  撤销条上写着"已删除…"（其实是第二张），点下去只回来第二张；
  而第一张的**文件已经被物理删除**了，`filesystem` 上再也找不回来。
  更难受的是撤销条还挂在那儿 5 秒，**看起来像是两张都能撤**。
- **建议**：把 undo 做成**一个小栈**（3–5 步），每步各自持有自己的 `onDiscard`，
  按撤销顺序逆序弹出；或至少在覆盖前**不允许**上一次的 `onDiscard` 立即执行
  （把文件删除推迟到"整个撤销链都过期"）。UI 上如果只能一步，就把撤销条做成
  "只能撤回最后一次"的明确措辞。
- **预期收益**：本机数据的删除是**没有云端可以回捞**的，多留几步的性价比很高。

## 八、应用内更新与可访问性

### 22. 下载不支持续传 · **P2**

- **代码依据**：`updatedownload.kt:86-110` 每次都是 `conn.inputStream` 从头读、写入
  `File(dir, "${target.name}.part")`，**没有 `Range` 请求头，也不复用已存在的 `.part`**；
  协程被取消时 `part.delete()`（`114-116`）。26MB 的包，走的是 GitHub 的重定向地址。
- **用户会怎么撞上**：在 4G 上下一半切到 Wi-Fi、或锁屏后被系统回收进程、或手一滑点了取消 ——
  **已经下的 20MB 全废**，重新从 0 开始。反复几次之后他会放弃，退回"自己去发布页下"。
- **建议**：支持 `Range: bytes=<已下载长度>-` 续传（`.part` 保留、`Content-Range` 校验、
  服务器不支持时自动退回整包）；下载期间建议配一个前台服务或至少提示用户"别切走"。
- **预期收益**：把弱网下的成功率从不稳定变成基本可用。

### 25. 装完的安装包留在 cache · **P3**

- **代码依据**：`updatedownload.kt:211-218`，`cleanOld()` 只在**下一次下载**时被调用
  （`112`）。装完之后没有任何地方去删那个 26MB 的 `LifeButler-vX.Y.apk`。
- **用户会怎么撞上**：在系统的"存储占用"里看到生活管家占了几十 MB，
  而且他不知道自己什么时候下过这么多东西。cache 理论上可被系统回收，但那不是保证。
- **建议**：`verify()` 通过并**成功调起安装界面之后**记一个标记，
  下次进「关于管家」时把已装过的包清掉；或者在版本号显示处给一个"清理安装包"的小入口。
  注意别在 `startActivity` 之后立刻删 —— 安装器是另一个界面，会读不到文件
  （这条坑 `readme` 里已经记过：分享附件同理）。
- **预期收益**：不留看不懂的空间占用。

### 23. 大字号"逐页过一遍"仍未做 · **P2**

- **代码依据**：`readme.md:191-193` 自己写着：清单建议的
  「1.3× 与 2.0× 两档字号逐页截图过一遍」**这一版没能做**，只做了静态排查与编译验证。
  v2.12 确实把 35 处小于 11sp 的文字提到了 11sp，也把 3 处承载文字的容器改成了 `heightIn(min=)`，
  但**"改了"不等于"放大后不截断"** —— 尤其是横向排布的状态胶囊、底栏标签、
  以及新加的 `lbDialogBody()`（限高 340dp）在超大字号下的表现。
- **用户会怎么撞上**：长辈把系统字体调到最大，某些行仍然会被裁掉半行 ——
  而这个产品的目标人群里就有他们。而这一条**只有截图才能证明**，读代码证明不了。
- **建议**：恢复设备可用后，用系统的「字体大小 / 显示大小」各拉一档，
  逐页截图比对（`grab_shot.py` 已经支持 `--open-tab` 直达，全程不用点击）。
  重点看：状态胶囊、列表副标题、底栏、三种弹窗的正文与按钮。
- **预期收益**：把唯一一条"文档说要做但没做"的老账清掉。

## 九、对外文案的一致性（属于「诚信约定」）

### 26. readme 有两处对不上 · **P3**

- **代码依据**：
  · `readme.md:3` 说「会联网的只有三处」（天气 / AI 管家 / 检查更新），

  版本号那句改成从 `app/build.gradle.kts` 同步（并加进发布清单的检查项）。
- **预期收益**：文案是产品承诺的一部分，自相矛盾最伤信任。

## 建议的动手顺序

1. **先修"说了却没做"的三条**（#1 备份静默漏文件、#2 恢复预览、#11 首页预算超支）——
   它们都属于"文档/界面承诺了、代码没做到"，与产品最核心的诚信约定直接冲突，
   而且改动都不大。**要么补上，要么把承诺改掉，不能挂着。**
2. **再做隐私闭环**（#3 通知不盖、#9 小组件明文）—— 应用锁已经做了，
   但漏掉的这两处会让用户觉得"锁了等于没锁"，性价比极高。
3. **然后补首页**（#4 / #12，同一处改动）—— 它决定"打开 App 就知道今天该干嘛"这句承诺成不成立。
4. **接着治可信度**（#6 自动落账改待确认、#13 假阳性）—— 自动捕获是差异功能，
   但一旦记错账，伤害面最大。
5. **补齐日常能力**（#5 补记日期、#17 自定义分类、#18/#19 列表性能）—— 属于"用得越久越重要"。
6. 其余 P2 / P3 按迭代节奏铺开。

## 验证方式（动手前先复现，别照着清单盲改）

清单里凡是标了 ⚠️ 的，都是**读代码得出、没有实测**。建议按下面的顺序取证：

1. **设备可用后先起模拟器**（`Pixel_8`，Android 14），走 `android-emulator-e2e-verify` 技能里的流程；
   注意这台 AVD 有冻结史，判据是 `adb shell` 空回 / `qemu CPU 8 秒增量 = 0`。
2. **不需要装机就能验的**：#1 / #2 / #3 / #5 / #6 / #21 都可以先用代码级自证 ——
   例如 #5 直接看 `addExpense` 的签名，#1 造一个"相册很多张"的状态跑一次 `exportState()`
   数一数字段里到底有几个文件。
3. **必须装机才能验的**：#9（桌面小组件实际显示什么）、#19 / #18（性能，要用大一点的数据集）、
   #23（字号 1.3× / 2.0× 截图逐页比对）。
4. **改完一定要跑一次 `:app:compileDebugKotlin`**（上一轮的 4 个编译错都是"自认为写完了"的欠账）；
   发版前按惯例自证产物内容（`verify_apk.py` + 新版独有字面量），**不要用字节数判断**。
